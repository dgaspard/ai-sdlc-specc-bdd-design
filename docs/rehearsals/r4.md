## Decisions the agent made, now mostly pinned by SPEC-06

- When a promotion, cash payment or repeat finalization needs the assigned
  veterinarian, it asks Reservation for the current one each time (D-66).
- Idempotency keys are scoped per bill for card and cash, and per reservation for
  booking fees. Requests for the same bill run one at a time, so two identical
  concurrent requests get one authorization. A same-key retry replays the
  original response, including the earlier bill snapshot or the original 502,
  and does not repeat the charge, credit or completion.
- Partial failures: if Customer doesn't confirm the credit, the bill doesn't
  count the payment. If the discount fails at Customer, no promotion is saved.
  Reservation's `already_completed` counts as success. Customer's
  `already_applied` counts as failure. r2 treated `already_applied` as success
  (GAP-14), so the two runs chose differently.

## New specification gaps reported

The agent found no specification that looked wrong. It reported two cases the
specs don't cover:

- **GAP-16: finalization can get stuck.** If the charge reaches Customer but the
  booking-fee credit then fails, no bill is saved. Every retry then gets
  `already_applied` from Customer and fails, so recovery is manual. No spec or
  test covers this case. It follows from treating `already_applied` as failure
  (see above).
- **GAP-17: attribution for administrator-only accounts in Checkout.** For an
  account with no veterinarian ID, a promotion records the user ID as
  `appliedByVeterinarianId`, and cash omits `recordedByVeterinarianId`.
  `visit-payment.feature` already marks this as an open follow-up. The seeded
  administrator is also a veterinarian, so the demo never reaches this case.
